## 4. Hallazgos detallados

### H1 — BAJA · CSP por `<meta>`, no por header HTTP

**Categoría**: OWASP A05:2025 — Security Misconfiguration (mitigación parcial)

**Ubicación**: `index.html` línea 7-8 (todos los HTMLs con CSP heredan este patrón).

**Descripción**: tu CSP es estricta y bien diseñada:
```
default-src 'self';
style-src 'self' https://cdnjs.cloudflare.com;
font-src 'self' https://cdnjs.cloudflare.com;
img-src 'self' data:;
script-src 'none';
object-src 'none';
base-uri 'self';
form-action 'self';
frame-ancestors 'none';
upgrade-insecure-requests;
```

`script-src 'none'` es la postura más segura posible (XSS muerto por construcción), y `frame-ancestors 'none'` ya cubre el caso de clickjacking sin necesidad de `X-Frame-Options`.

**Pero**: cuando CSP se entrega por `<meta http-equiv>` hay dos diferencias con un header HTTP:
1. **No se puede usar `report-uri` ni `report-to`** (la directiva `report-uri` está deprecada, `report-to` solo funciona en header). Pierdes telemetría de violación.
2. **Algunos navegadores antiguos no la aplican** a la primera petición (aunque en navegadores modernos funciona desde el primer paint).
3. **GitHub Pages no permite inyectar headers custom en la respuesta HTTP** salvo usando un service worker o un proxy (Cloudflare por delante). Por eso lo haces con `<meta>`.

**Riesgo real**: muy bajo. Tu CSP es estricta y tu sitio no tiene contenido dinámico que genere inyecciones.

**Remediación propuesta (NO aplicada)**:
- Si en algún futuro pones Cloudflare delante, mover CSP a header real y añadir `report-to` con un endpoint de reporte.
- Mientras tanto, mantener como está. **No cambiar**.

**Fuente**: https://owasp.org/www-project-secure-headers/ — sección CSP.

---

### H2 — BAJA · Falta `X-Frame-Options` por header

**Categoría**: OWASP A05:2025 — Security Misconfiguration

**Descripción**: la cabecera `X-Frame-Options: DENY` no está en la respuesta HTTP de GitHub Pages. **Pero** tu CSP incluye `frame-ancestors 'none'`, que es el reemplazo moderno y cumple la misma función en navegadores actuales.

**Riesgo real**: muy bajo. Los navegadores modernos (Chrome 79+, Firefox 74+, Safari 12.1+) ignoran `X-Frame-Options` si hay `frame-ancestors` en CSP. Solo navegadores muy antiguos (legacy) lo necesitan.

**Remediación propuesta (NO aplicada)**:
- No es accionable directamente en GitHub Pages sin proxy.
- Si en algún momento se sirve por un servidor propio, añadir `X-Frame-Options: DENY` por header además de la CSP.
- Mientras tanto, la CSP es suficiente.

**Fuente**: https://owasp.org/www-project-secure-headers/#x-frame-options

### H3 — BAJA · `access-control-allow-origin: *`

**Categoría**: OWASP A05:2025 — Security Misconfiguration (informativo)

**Descripción**: GitHub Pages sirve tu sitio con `access-control-allow-origin: *` en la respuesta. Esto es **deliberado de GH Pages** porque sirve como CDN para muchos sitios.

**Riesgo real**: ninguno para tu caso. Tu sitio es HTML estático, no sirves datos JSON, no hay endpoints API, no hay credenciales. Un atacante no puede extraer nada sensible mediante una petición CORS porque no hay nada sensible que extraer.

**Cuándo SÍ sería un problema**: si en algún futuro sirves un endpoint `/api/*` que devuelva datos del usuario, esa respuesta también llevaría `*` y cualquier origen podría leerla. Hoy no aplica.

**Remediación propuesta (NO aplicada)**:
- Mantener como está. No es accionable.
- Si en el futuro hay API: poner Cloudflare delante con CORS restrictivo.

**Fuente**: https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Access-Control-Allow-Origin

### H6 — INFO · Un uso de `innerHTML` en `TryHackMe/viewer.html`

**Categoría**: OWASP A05:2025 — Injection (a revisar manualmente)

**Ubicación**: `TryHackMe/viewer.html`

**Descripción**: `grep` encontró un uso de `innerHTML`. No he leído el archivo (no lo has pedido), pero es un punto a revisar manualmente si algún día lo modificas.

**Riesgo potencial**: si `innerHTML` se usa con datos del usuario (sin sanitizar), hay XSS. Aunque tu CSP tiene `script-src 'none'`, eso mitiga la ejecución de `<script>` inyectado vía innerHTML, pero **CSP no bloquea event handlers inline** (`<img onerror=...>`) si la directiva `script-src` permite `'unsafe-inline'`. Tu CSP tiene `script-src 'none'`, así que está cubierto incluso con innerHTML.

**Riesgo real**: muy bajo, gracias a CSP.

**Remediación propuesta (NO aplicada)**:
- Cuando edites `TryHackMe/viewer.html`, usa `textContent` en lugar de `innerHTML` donde sea posible (es lo que recomienda tu propio `PasswordGenerator/generator.js` como patrón).
- Si necesitas HTML, sanitiza con DOMPurify o similar.
